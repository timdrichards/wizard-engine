# Wizard Extensions: Version 1 vs Version 2

Two builds of the same extension framework, compared on the same two extensions, so we can choose a direction.

- **Version 1** (branch `ext-v1`) uses only what Virgil has today.
- **Version 2** (branch `ext-v2`) uses open enums with per-case methods: Eliot's titzer/virgil#653, rebased onto current Virgil with six fixes in timdrichards/virgil branch `open-enums-rebased`.

Both implement `undo` (memory checkpoints) and `ministe`, a single-threaded subset of Wasm Simple Transactions with STE's encodings. Eliot's transactional Wizard was a reference for what a real extension needs. None of its code is used.
The design itself is in [Extensions.md](Extensions.md).

Measured 2026-10-27 in an x86-64 Linux container on Apple silicon (Rosetta). Configurations are paired so that each version is built with a compiler from the same Virgil base:

- master and V1 with upstream Virgil `908c7e2`;
- master and V2 with `908c7e2` plus open enums (`349669e`).

## Recommendation

**Build on Version 1 now, and plan to move to Version 2 when open enums land.**

- V2 is the better way to write an extension:
  - each instruction is one enum case with its own methods;
  - the core loses the `EXT` placeholder, the parallel tables and the registration list;
  - forgetting to register an instruction becomes impossible.
- But the language feature it needs is not ready. Making Wizard work with #653 took six compiler fixes, including a native miscompile and an initialization-order bug. With default options, V2 also costs more code space on every target.
- Moving from V1 to V2 is mechanical. The hooks are the same, both extensions were rewritten in an afternoon, and the same test files pass unchanged on both.

## How the two differ

The same instruction in each version:

```
// Version 1: a class per instruction, listed by its extension.
class UndoBegin extends UndoOp {
	new() super(0x00, "undo.begin", SigCache.v_v) { }
	def interpret(f: ExtFrame) -> TrapReason { return UndoLogs.of(f.instance()).begin(); }
}
class UndoExtension extends InstrExtension {
	def opcodes() -> Array<ExtOpcode> { return [UndoBegin.new(), UndoCommit.new(), ...]; }
}
// plus src/ext/undo/extension.txt: "UndoExtension.new()"

// Version 2: a case of an open Opcode enum.
enum Opcode.Undo {
	BEGIN(0xF9, 0x00, "undo.begin", ImmSigs.NONE, SigCache.v_v) {
		def interpret(f: ExtFrame) -> TrapReason { return UndoLogs.of(f.instance()).begin(); }
	},
	...
}
```

| | Version 1 | Version 2 |
|---|---|---|
| An instruction is | an `ExtOpcode` subclass | a case of `enum Opcode.<Name>` |
| In the opcode tables | `Opcode.EXT` plus a parallel `ExtOpcode` table | the `Opcode` case itself |
| Registration | a list generated by `build.sh` from `--ext` and each `extension.txt` | none: compiling the extension's files is enough |
| Core `match` over `Opcode` | an `EXT` arm, then a lookup of the descriptor | the existing `_` arm calls the case's method |
| Shared behavior | a base class; Virgil has no `super.method()`, so shared checks are named helpers | subtype-level methods, which cases override |
| Floating (internal one-byte) opcodes | `OpcodeClaim.FLOATING` | an `isFloating()` override |

The engine seams are the same in both: write observer and page tracking, per-instance state, block-shaped instructions with an `end` rewrite, `runtime_EXT`, and compiler bailout.

Each scenario was done on both branches (`scenarios-v1`, `scenarios-v2`), built, and tested.

### Speed

- **Virgil bootstrap** (the compiler compiling itself twice, 3 runs): about 7.4 s for upstream and 7.0 s with open enums. That is the same within noise.
- **Compiling Wizard:** 0.5 to 2.4 s per target in every configuration, with no consistent difference.
- **Virgil benchmarks** (BubbleSort, Fannkuch, MatrixMult, DeltaBlue and Mandelbrot compiled to Wasm; no extension instructions; 5 runs):
  - With the jit, all six builds are the same within ±1 run-to-run step (0.13 to 0.19 s).
  - In the fast interpreter, results swing ±20% between builds in no consistent direction. Even master built by the two compilers differs by up to 15%.
  - This is the code-layout sensitivity first seen in step 4. Under Rosetta it hides any real difference, and these numbers need repeating on native x86-64 hardware.
- **Extension instructions** (200,000 iterations; median of 5; seconds):

| Loop body | V1 int | V2 int | V1 jit | V2 jit |
|---|---|---|---|---|
| `block` + `i32.store` (no extension) | 0.10 | 0.11 | 0.10 | 0.10 |
| `undo.begin` + `i32.store` + `undo.commit` | 4.77 | 4.80 | 4.82 | 4.84 |
| `tblock` + `i32.tstore` + `end` | 3.14 | 3.12 | 3.14 | 3.14 |
| `tblock` + `i32.store` + `end` (page fault path) | 4.87 | 4.84 | 4.87 | 5.08 |

  V1 and V2 are the same. A short transaction costs about 15 to 24 µs, in both versions. The time goes into transaction setup: page protection, the shadow buffer and a page copy. Dispatching the extension instruction is not where it goes, so this is the place to optimize. The jit gives nothing here because functions using extension instructions stay in the interpreter.

### Correctness

- Full Wizard suites (spec tests pinned to the 2026-10-20 spec commit) on x86-64-linux, all five modes, and on v3i:
  - V1, V2 and master give identical results, apart from the 6 extension registry unit tests;
  - master built with the open-enum compiler is identical to master built with upstream.
- Extension tests: 108 pass on the four x86-64-linux test tiers and 36 on v3i, in both versions. Mutation checks fail exactly the rollback tests.
- Open-enum compiler: Virgil's enums suite passes 310/310 on v3i, x86-64-linux and jar. core, variants, cast, open_types, fsi32, fsi64, float, layout, funexpr and stacktrace match upstream.

## What Version 2 needed in Virgil

#653, rebased onto `908c7e2` (63+ conflict hunks; notes in the commit), then six fixes, each with a test:

1. Per-case overrides on cases of a subtype enum that does not declare the method crashed the compiler (`IrBuilder.addVstMethod`).
2. **Native miscompile:** on x86-64, a subtype case's override was ignored and the subtype's method called. v3i was correct. A live case class reached only its immediate parent's `subtypes`, so the root's method table never saw it.
3. The synthesized `shortName` member clashed with an enum's own `shortName` field (Wizard's `DbgCommand2`).
4. `E.count` and `for (e in E)` covered only the root's own cases.
5. Cases produced by iteration were never marked live, so a native method call on one hit an empty slot.
6. **Initialization order:** reading an enum field did not initialize subtype enums. A component initializer that iterated `Opcode`, as Wizard's `Opcodes` does, saw null fields for every extension case. This is the problem Ben raised about initialization order. It is now fixed in the compiler, by initializing the whole hierarchy before a field read.

Also dropped: `open_types/name0-3` from #653, written in the removed `type A.B` syntax. Rewritten with `extends`, they crash upstream itself in `MethodEnv.lookupVariantCaseMember`, which is a separate issue.

## Other findings

- **New spec tests fail on master.** `memory64/table_grow64` and `exceptions/cast`, pulled from the spec repository on 2026-10-27, fail on unmodified Wizard master (a BoundsCheckException in `Table.grow` and a TypeCheckException in `Runtime.castObject`).
- **`OpcodePage`'s `[code]` operator** reads the top-level page even for a code on a subpage. The core uses `Opcodes.find`, so this has not mattered.
- **A collision error stops the build,** but on native targets the message is lost: `System.error` cannot run at compile time (open question 7 in Extensions.md).
- **The placeholder case shows up in loops.** In a build without extensions, `for (op in Opcode)` in V2 yields the open enum's `_` placeholder, whose fields are null. Loops over every opcode must skip it, as V1's loops skip `EXT`.
